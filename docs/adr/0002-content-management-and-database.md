# ADR 0002: コンテンツ管理とDB導入時期を分ける

- Status: Accepted
- Date: 2026-10-02
- Scope: プロフィール、プロジェクト、スキル、活動実績、画像の管理

## Context

「作品を気軽に追加できる」ことは将来の重要な要件だが、気軽さには複数の意味がある。

- GitHubへデータファイルを追加すればよい
- ブラウザの管理画面から入力したい
- 画像もブラウザからアップロードしたい
- 保存後すぐに本番へ反映したい

DBだけを導入しても、管理画面、認証、画像ストレージ、公開反映、バックアップが自動的に得られるわけではない。そのため、更新方法を判断してからDBを選ぶ。

## Decision

### 初期フェーズ

React化の初期は、プロジェクトや活動実績をTypeScriptまたはJSONのデータとしてリポジトリ内に置く。コンポーネントはデータの取得元を直接意識しないよう、`lib/content`などに境界を置く。

この段階では、GitのPull Requestを公開前レビューとバックアップとして利用する。

### DB導入時

次のいずれかが必要になった時点で、DBと管理画面を再評価する。

1. ブラウザから非開発者が編集する必要がある。
2. 画像を管理画面からアップロードしたい。
3. GitHubへの変更なしに公開したい。
4. 公開・非公開、表示順、下書きなどの状態管理が必要になる。
5. プロジェクト、活動、記事などのコンテンツが増え、データファイルの編集が負担になる。
6. 複数人がコンテンツを更新する。

特に1〜3のいずれかは、DB・管理画面導入の強いトリガーとする。

### 第一候補

DB、認証、画像ストレージをまとめて導入する場合の第一候補はSupabaseとする。

想定構成は次のとおり。

```text
projects
project_media
skills / skill_groups
activities
profile / social_links
users または Supabase Auth
```

画像本体はStorage、DBにはURL、altテキスト、表示順、メディア種別を保存する。管理操作は認証済みユーザーだけに許可し、クライアントへサービスロールキーを公開しない。

### Cloudflare中心に寄せる場合

Cloudflareの実行基盤を優先する判断になった場合は、D1をDB、R2を画像ストレージ候補とする。ただし、認証、管理UI、Next.jsの実行方式、バックアップ、ローカル開発体験をSupabase案と比較してから決める。DB製品はこのADRだけで固定しない。

## Decision criteria

DB導入時は、次の順で評価する。

| 基準 | 確認すること |
| --- | --- |
| 更新体験 | 作品追加がフォームだけで完了するか |
| 公開反映 | 保存後にいつ公開されるか。再ビルドが必要か |
| 認証・権限 | 管理者以外が編集できないか |
| 画像管理 | サイズ、alt、削除、差し替え、配信URLを管理できるか |
| SEO | 公開ページがサーバーまたはビルド時にHTML化されるか |
| 運用 | バックアップ、障害時の復旧、費用を把握できるか |
| ロックイン | DBやストレージを移行できるデータ形式か |
| 複雑性 | 個人ポートフォリオの規模に対して過剰でないか |

## Consequences

### Positive

- React化とDB設計を分離できる。
- 最初はGitで安全にレビュー・復旧できる。
- DB導入時もコンテンツ取得境界を差し替えやすい。
- 「DBを入れたが結局直接SQLを編集する」状態を避けられる。

### Negative

- DB導入まで管理画面は存在しない。
- データ移行時に、既存のTypeScript/JSONからDBへ変換する作業が必要になる。
- DB導入後は認証、RLS、バックアップ、画像削除などの運用責任が増える。
